# 실증 계획: 보강 아이디어와 차등 커버리지 실험 설계

> 현재 논문에는 "본 모델이 기존 방법보다 낫다"를 보이는 장치가 없음 (5.6절 elicitation 질문과 6장 PoC는 모두 단독 적용).
> "DFD로는 표현 안 된다"고 1장에서 주장해 놓고 그 주장을 실험으로 확인하지 않은 상태.

## 보강 아이디어 5가지 (우선순위 순)

### 아이디어 1: 차등 커버리지 실험 (Differential Coverage Study) — 가장 강력
동일 시스템에 ① DFD+STRIDE, ② MAESTRO, ③ 본 모델을 각각 적용, **"③에서만 도출되는 위협"** 을 보임. 상세 설계는 아래.

### 아이디어 2: 실제 공개 사고의 TB 매핑 — 비용 대비 최고, 시작점으로 권장
EchoLeak(M365 Copilot zero-click), ChatGPT 메모리 오염, Slack AI 유출 등 실제 사고를 TB-1~9에 매핑. "실제 공격 사슬이 TB-3→TB-6→TB-7→TB-8을 통과했다"는 사후 분석은:
- 모델이 현실을 설명한다는 증거
- **"crossing chain"(단일 boundary가 아닌 crossing 시퀀스)** 이라는 새 분석 단위를 자연스럽게 도출 — 별도 기여로 승격 가능
- 작성 과정에서 TB 정의의 허점(예: 응답 반환 경계 부재)이 드러나 모델 자체가 단단해짐

### 아이디어 3: Typed-DFD 표기법의 형식화 — 학술적 무게
edge에 5개 타입(data/control/privilege/re-entry/evidence)을 부여한 typed DFD 정의 + 타입별 기본 질문 세트 도출 규칙 + "기존 DFD는 모든 edge가 data 타입인 특수 케이스"(하위 호환성) 증명. 기여가 "카탈로그"(경쟁 많음)에서 "표기법과 도출 규칙"(경쟁 적음)으로 이동.

### 아이디어 4: 방어 메커니즘 배치 지도 (Defense Placement Map)
기존 방어들을 TB별 매핑: PFI→TB-6, SEAgent/MAC→TB-7, ScopeGate→TB-7, 입력 필터→TB-1, lattice labeling→TB-3/4. 선행연구가 경쟁자가 아니라 **본 모델 좌표계 위에 배치되는 대상**이 됨. "어느 TB에는 아직 방어 연구가 없는지"(예: TB-9 audit integrity)를 드러내는 gap 분석 포함. SoK 논문으로 전환 시 뼈대.

### 아이디어 5: PoC 권한 이원화 실험
동일 시나리오를 (A) read-only token, (B) service account + 검색 문서에 간접 인젝션 삽입으로 실행 → B에서만 외부 기록 오염 재현. 4장 표 N과 TB-7 논증의 실증. LLM 호출 포함 필수, LangGraph 기준 며칠 규모.

### 투고처별 조합
- **산업 컨퍼런스**: 아이디어 2 + 4 + 5 (사고 매핑·배치 지도는 실무 즉시 유용, 권한 이원화는 발표 하이라이트)
- **학술 학회**: 아이디어 1 + 3 필수, 2를 보조 증거로. 또는 아이디어 4를 뼈대로 SoK 재구성

# 아이디어 1 상세 설계: Seeded-Vulnerability 기반 4-Arm 차등 커버리지 실험

## 핵심: 정답을 미리 심어두고(seeded vulnerabilities), 각 프레임워크의 절차가 그 정답에 도달하는지 측정 → 채점 가능한 recall 실험

## 1단계: 대상 시스템 — 6장 PoC 확장 + 결함 7개 심기

6장 LangGraph PoC에 **LLM 호출 추가(필수)** 후 다음 결함을 심음:

| # | 심는 결함 | 대응 TB | 설계 의도 |
|---|---|---|---|
| V1 | API endpoint 인증 누락 | TB-1 | **대조군**: 전통 DFD+STRIDE도 잡아야 함 — strawman 비판 차단 |
| V2 | 검색 문서 내 간접 프롬프트 인젝션 | TB-3/4 | RAG→Context edge가 DFD에선 평범한 data flow |
| V3 | system instruction과 RAG 내용을 구분자 없이 연결 | TB-4 | "trust level 결합" 기준이 있어야 보임 |
| V4 | 모델 출력을 스키마 검증 없이 tool call로 파싱 | TB-6 | data→control 전환 지점 |
| V5 | 사용자 권한 무관하게 항상 service account로 도구 실행 | TB-7 | **핵심**: confused deputy — DFD에서 구조적으로 안 보임 |
| V6 | tool result를 출처 표시 없이 memory 저장, 다음 세션 재사용 | TB-8 | 1회성 이동 vs 반복 재유입 구분 필요 |
| V7 | audit에 routing 결정만 기록, 근거 model output 미기록 | TB-9 | evidence 별도 축 필요 |

## 2단계: 4개 Arm

- **Arm 0**: 무 프레임워크 ("이 시스템의 위협을 찾아라") — **오염 통제용 대조군**
- **Arm A**: DFD + STRIDE-per-element (MS 표준 절차)
- **Arm B**: MAESTRO (CSA 공식 layer별 카탈로그)
- **Arm C**: 본 모델 (5.3 식별 기준 → TB 도출 → 5.6 elicitation 질문)

측정값 = 각 arm의 발견 − Arm 0의 발견 = **프레임워크의 순수 유도 효과(guidance effect)**

## 3단계: 분석자 — LLM 대체 (결정됨)

### LLM 대체의 장점
- **재현성**: 프롬프트·모델 버전·전체 트랜스크립트 공개 시 누구나 재현 (인간 실험은 불가능)
- **반복 측정**: 3개 모델 × arm당 5~10회 → "우연" 통계적 배제
- **공정성 통제 용이**: 동일 모델·온도·토큰 예산으로 세 arm 실행

### 반드시 막을 함정 3가지
1. **오염(contamination)**: LLM은 confused deputy를 사전지식으로 앎 → STRIDE arm에서도 찾을 수 있음. **해결: Arm 0** — 측정값을 유도 효과로 전환
2. **프롬프트 불공정**: Arm C 프롬프트가 은연중 더 정교하면 실험 무효. 해결: 각 arm에 해당 프레임워크 **공식 문서 원문**을 그대로 삽입, 감싸는 템플릿 동일, 연구 목적·심은 취약점·비교 실험 사실 미포함(blind), 프롬프트 전문 부록 공개
3. **채점 순환**: 채점까지 LLM에 시키면 순환 논증. **해결: 채점만 인간** (사내 엔지니어 1~2명, 루브릭 채점, inter-rater agreement 보고) — 분석(비싼 부분)은 LLM, 채점(싼 부분)만 인간

### 측정 대상의 변화 (정직하게 명시할 것)
증명하는 것은 "인간 실무자가 더 잘 찾는다"가 아니라 "**동일 분석 역량에서 프레임워크 절차의 유도 효과가 있다**" — 프레임워크 논문이 증명해야 할 것이 정확히 이것이므로 약화가 아님. Limitations에 인간 일반화는 후속 연구로 명시. 학술 venue면 소규모 인간 파일럿 보조 권장.

### 부수 기여
Arm 0에서 "LLM도 유도 없이는 flow 전환 지점을 놓친다"가 나오면 → "본 모델은 AI 기반 자동 threat modeling 도구(ASTRIDE 등)의 유도 장치로도 유효" — 두 번째 기여.

## 4단계: 채점 — "정밀도 사다리" (핵심 de-risk 장치)

이진 탐지(찾았다/못 찾았다)로는 LLM 사전지식 때문에 차이가 안 날 위험 큼. 지표를 4단계 사다리로:

1. **탐지**: 위협 존재 언급 — 세 arm 모두 비슷할 것으로 예상
2. **위치 특정**: 아키텍처의 어느 edge에서 발생하는지
3. **메커니즘 특정**: V5라면 "principal grant와 credential의 불일치"까지
4. **통제 배치**: "어디에 무슨 통제를 넣어야 하는지" 도출 여부

**예상: 1단계 차이 없음, 3~4단계에서 벌어짐.** 구조적 이유: MAESTRO 문서에는 Orchestrator 내부 edge 개념이 없어 Layer 3 체크리스트가 분석자를 "Tool Dispatcher 앞 grant-credential 대조 지점"까지 유도할 방법이 없음 — 이 해상도 차이는 LLM 사전지식으로 안 메워짐.

채점 기준 사전 고정: "메커니즘 특정=발견 / 범주 지적(예: 'tampering 가능')=부분 / 무언급=미발견"

## 5단계: 사전 가설 (반증 가능성)

- **H1**: flow 전환 지점 결함(V4/V5/V6)은 Arm C만 메커니즘 수준 발견
- **H2**: 전통 결함(V1)은 전 arm 발견 (Arm C가 기존 커버리지를 잃지 않음)
- **H3**: MAESTRO는 V5를 'tool misuse' 범주로 짚지만 메커니즘 특정에 못 미침

가설 사전 명시 → 결과가 달라도 정직한 발견으로 보고 가능. 최악(차이 전무)에도 "LLM 시대 프레임워크 유도 효과는 탐지가 아니라 정밀도에서 갈린다"는 부차 발견으로 전환 가능.

## 결과물
7×4 매트릭스 (행=V1~V7, 열=Arm 0/A/B/C, 셀=사다리 단계 + 근거 한 줄) — 1장의 "DFD에는 구분해 표현할 방법이 없다"는 주장을 측정 가능한 증거로 전환.

## 실행 가능성 평가 (정직한 판단)

| 항목 | 평가 |
|---|---|
| 기술적 실행 | **확실히 가능** — PoC 확장 며칠~2주, 3-arm 적용·채점 1주 |
| 이진 탐지 기준 차이 | 위험 (절반 이하 확률) — LLM 사전지식 |
| 정밀도 사다리(3~4단계) 기준 차이 | **상당히 높은 가능성** — 구조적 해상도 차이 (단, 추정이지 보장 아님) |
| 보험 | 매핑 표 + 사고 매핑은 실패 불가능한 실증으로 병행 |

## 다음 단계: 저비용 파일럿

본 실험 투자 전 드라이런: PoC 시스템 설명서 1부 + 4-arm 프롬프트 작성 → LLM 몇 개에 실행 → 사다리 채점 → 3~4단계 차이 신호 확인. 신호 있으면 본 실험 확정, 없으면 seeded vulnerability/지표 수정.

**주의**: 이 논문 내용과 실험 의도를 아는 세션/모델이 분석자 역할을 하면 오염된 파일럿 — 설계 검증용으로만 쓰고, 본 실험은 맥락 없는 별도 세션으로 실행할 것.

## 예상 일정
